# PugWork Day 7 — Full-Stack Employee Hub

> Day 7 upgrade of the Day 6 PugWork employee dashboard: a Next.js App Router frontend + Node.js/Express REST API, with a layered backend, validation, demo authentication, and persistent JSON-file storage for local learning.

- Day 6 reference app: https://pugarch-day-6-employee-hub.onrender.com/

## 1. Project overview

PugWork helps a small People Operations team maintain an employee directory through a responsive dashboard. Day 7 turns the original client-side prototype into a full-stack learning project: the Next.js app calls a separately running Express API, and the API validates requests and persists employees to a JSON file.

## 2. Problem statement

A dashboard that stores data only in browser `localStorage` cannot provide a single shared source of truth across browsers or users. Teams need a central API, validated operations, consistent error responses, and a clear separation between UI, HTTP routes, business rules, and data access.

## 3. Features

### Frontend (`nextjs-app`)
- Next.js App Router with shared root layout and loading/error/not-found states.
- `/employees` directory with search, department/status filters, sort order, summary metrics, and responsive table/cards.
- `/employees/create` form with client-side validation and API error feedback.
- `/employees/[id]` detail page with employee data and edit/delete actions.
- Server Components for initial page structure and Client Components for interactive controls/forms.
- API base URL configured through an environment variable.
- Empty, loading, validation, success, and error states.

### Backend (`node-api`)
- Express REST endpoints: `GET`, `POST`, `PUT`, and `DELETE` employee operations.
- Layered structure: routes → controllers → services → models; shared middleware and utility functions.
- Zod request validation, centralized error handling, request IDs, Helmet, CORS, and JSON body limits.
- Demo JWT authentication for write operations; reads are public in this learning version.
- JSON-file persistence for local development, with seeded example employees.
- Health endpoint and consistent JSON response envelopes.

### Senior-level extension ideas
- Replace JSON storage with PostgreSQL + Prisma migrations.
- Add role-based permissions, audit logs, pagination, optimistic UI, rate limiting, tests, Docker, and CI.
- Add employee lifecycle workflows, onboarding checklists, leave requests, and department analytics.

## 5. Architecture

```text
Browser
  |
  v
Next.js App Router (Server + Client Components)
  |  NEXT_PUBLIC_API_BASE_URL
  v
Express REST API
  |
  +--> routes/          HTTP path and method mapping
  +--> controllers/     request/response handling
  +--> services/        business rules
  +--> models/          JSON persistence adapter
  +--> middleware/      auth, validation, errors, request IDs
  +--> utils/           AppError and async helpers
  |
  v
data/employees.json (local development only)
```

## 6. Database design

This Day 7 starter uses a JSON file to make the project runnable without a database server. It is not suitable for multi-instance production deployment. The `Employee` record has:

| Field | Type | Rules |
|---|---|---|
| `id` | string | generated UUID |
| `firstName` | string | required, 2–60 chars |
| `lastName` | string | required, 2–60 chars |
| `email` | string | required, valid and unique |
| `role` | string | required |
| `department` | enum | Engineering, Product, Design, HR, Marketing, Finance, Operations |
| `status` | enum | Active, On Leave, Inactive |
| `salary` | number | positive |
| `location` | string | required |
| `joinDate` | ISO date string | required |
| `createdAt`, `updatedAt` | ISO date strings | generated by API |

**Production recommendation:** use PostgreSQL with a unique constraint on `email`, migrations, transactions, and backups.

## 7. API documentation

Base URL locally: `http://localhost:4000/api/v1`

| Method | Endpoint | Auth | Purpose |
|---|---|---|---|
| GET | `/health` | No | API health check |
| POST | `/auth/login` | No | Get a demo JWT |
| GET | `/employees` | No | List employees; supports `q`, `department`, `status`, `sort` |
| GET | `/employees/:id` | No | Read one employee |
| POST | `/employees` | Bearer token | Create employee |
| PUT | `/employees/:id` | Bearer token | Replace editable employee fields |
| DELETE | `/employees/:id` | Bearer token | Delete employee |

### Login

`POST /api/v1/auth/login`

```json
{
  "email": "admin@pugwork.local",
  "password": "PugWork@123"
}
```

Example response:

```json
{
  "success": true,
  "data": {
    "token": "<JWT>",
    "tokenType": "Bearer",
    "expiresIn": "2h"
  }
}
```

### Create employee

`POST /api/v1/employees` with `Authorization: Bearer <JWT>`:

```json
{
  "firstName": "Aarav",
  "lastName": "Sharma",
  "email": "aarav.sharma@example.com",
  "role": "Frontend Engineer",
  "department": "Engineering",
  "status": "Active",
  "salary": 85000,
  "location": "Jabalpur",
  "joinDate": "2026-01-15"
}
```

### Common response envelope

Success:

```json
{ "success": true, "data": {} }
```

Error:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": []
  }
}
```

HTTP status codes include `200`, `201`, `400`, `401`, `404`, `409`, and `500`.

## 8. Installation

Requirements: Node.js 20 or newer and npm.

Open two terminals.

### Terminal A — API

```bash
cd day-07/node-api
copy .env.example .env
npm install
npm run dev
```

The API runs at `http://localhost:4000`.

### Terminal B — Next.js app

```bash
cd day-07/nextjs-app
copy .env.example .env.local
npm install
npm run dev
```

The frontend runs at `http://localhost:3000`.

The API and frontend must both be running for employee operations to work.

## 9. Environment variables

### `node-api/.env`

```env
PORT=4000
NODE_ENV=development
CLIENT_ORIGIN=http://localhost:3000
JWT_SECRET=replace-this-with-a-long-random-secret-before-use
JWT_EXPIRES_IN=2h
ADMIN_EMAIL=admin@pugwork.local
ADMIN_PASSWORD=PugWork@123
DATA_FILE=./data/employees.json
```

### `nextjs-app/.env.local`

```env
NEXT_PUBLIC_API_BASE_URL=http://localhost:4000/api/v1
```

Never commit `.env` or `.env.local`. The demo admin password is for local learning only; replace it before sharing or deploying. `NEXT_PUBLIC_*` values are exposed to the browser and must never contain secrets.

## 10. How to run

1. Start the Express API in Terminal A.
2. Start the Next.js app in Terminal B.
3. Open `http://localhost:3000/employees`.
4. Browse, search, filter, and sort the employee directory.
5. Use **Add employee** to sign in with the demo admin credentials and create a record.
6. Open an employee detail page to edit or delete the record.
7. Check `node-api/data/employees.json` to see local persistence.

### Useful API commands (Windows CMD)

```bash
curl http://localhost:4000/api/v1/health
curl http://localhost:4000/api/v1/employees
```

To test protected writes, first login at the frontend or call `/api/v1/auth/login` and pass the returned token in an `Authorization: Bearer <token>` header.

## 13. Challenges faced and solutions

- **Separating frontend and backend:** use a dedicated API base URL and keep UI code independent of data storage.
- **Keeping route handlers maintainable:** use routes, controllers, services, and models instead of writing all logic in one file.
- **Invalid or duplicate employee data:** validate request bodies and enforce email uniqueness in the service/model layer.
- **Consistent errors:** centralize error mapping and return predictable JSON envelopes.
- **Protected write operations:** require a JWT for create, update, and delete requests.
- **Local persistence without database setup:** use a JSON-file adapter, while documenting its limits for production.

## 15. Security and learning notes

This is an educational Day 7 implementation, not a production HR system. The JSON-file store is not safe for concurrent multi-process writes, demo credentials must be changed, and JWT secrets must be strong and private. Do not use real employee personal or payroll information in this starter.
